# 기록 증분 동기화

평소 자동 동기화는 서버의 변경된 기록을 페이지로 조회하고, SQLite에서도 해당 ID만 반영한다. 최초 복원과 복구용 전체 조회는 유지하되 전체 조회에서도 값이 같은 기록을 다시 쓰거나 화면에 변경 알림을 보내지 않는다.

## 조회와 복구

- 새 설치·새 계정·이전 버전에서 업그레이드하여 체크포인트가 없는 경우에는 기존 전체 조회로 시작한다. 정렬 쿼리에서 누락될 수 있는 잘못된 서버 문서도 최초 전체 조회에서 검증한다.
- 이후 자동 동기화는 `serverUpdatedAt`과 문서 ID 순서로 최대 100개씩 받는다. 삭제도 기존 tombstone을 같은 쿼리로 받는다.
- 각 조회 시작 시 서버의 최신 위치를 상한으로 고정한다. 조회 도중 계속 새 기록이 생겨도 이번 작업이 무한히 뒤를 따라가지 않는다. 이후 변경은 다음 동기화에서 가져온다.
- 페이지 사이에서는 timestamp와 ID 이후부터 조회한다. 새 동기화·앱 재시작에서는 마지막 timestamp를 포함하여 다시 읽어, 동일 시각에 변경된 다른 ID도 놓치지 않는다. timestamp는 초·나노초로 보존한다.
- 빈 결과에서 기기 시각을 서버 커서로 저장하지 않는다. 빈 계정도 초기화 완료 위치를 저장하므로 매번 전체 복원하지 않는다.
- 동기화 화면에서 직접 실행하는 수동 동기화, 마지막 전체 검증 후 24시간이 지난 경우, 기기 시각이 이전으로 바뀐 경우에는 전체 조회로 재검증한다. 관리자에 의한 과거 시각 덮어쓰기·물리 삭제처럼 정상 앱의 timestamp/tombstone 계약 밖에서 발생한 변경도 전체 재검증으로 확인한다.
- 24시간은 기기에서 다음 동기화를 실행할 때 판단하는 기준이다. 앱이 종료되어 있는 동안 예약 작업을 실행하는 기능은 아니다.

같은 timestamp의 문서가 많으면 해당 묶음은 다음 동기화에서도 다시 조회한다. 변경이 없는 경우에도 최신 위치 확인과 마지막 timestamp 묶음 조회는 필요하므로, 서버 읽기가 항상 0회가 되는 방식은 아니다.

## 로컬 반영과 데이터 보호

받은 페이지의 기록·삭제·버전 메타데이터·체크포인트를 같은 SQLite 트랜잭션에서 확정한다. 실패하면 해당 페이지와 진행 위치를 함께 롤백하고, 이미 완료한 이전 페이지는 유지한다.

미완료 Outbox·미해결 충돌·무료 기간 변경 이력이 있으면 먼저 처리하거나 동기화를 중단하여 로컬 의도를 보호한다. 처리 중 계정·세션이 바뀌면 페이지를 반영하지 않는다. 저장된 기기 사진은 DB의 현재 값에서 보존한다.

같은 데이터가 다시 내려오면 본문·조과·사진·메타데이터의 불필요한 쓰기와 화면 알림을 생략한다. 메모리 캐시만 비우는 경우에는 체크포인트를 유지하고, 실제 기록 캐시 초기화와 계정 데이터 삭제에서는 체크포인트도 함께 삭제한다.

Outbox의 상태 변경과 재시도는 해당 행만 UPDATE하고 단건으로 확인한다. payload와 삽입 순서를 보존하며, 서버 성공 응답 처리도 전체 대기열을 다시 읽지 않고 변경 항목만 캐시에 반영한다.

## 검증 범위와 측정 기준

- 저장소 회귀 테스트는 변경 ID의 SQL 작업, 동일 페이지 재조회 시 쓰기·알림 생략, 사진 보존, 로컬 변경·세션 보호, 체크포인트 롤백과 초기화를 검증한다.
- Outbox 테스트는 상태 변경 시 전체 payload 조회와 payload 재쓰기가 없고, 단건 조회·UPDATE만 발생하는지 계수한다.
- 통합 테스트는 초기 복원 이후 증분 조회, 동일 timestamp 페이지 경계, 중간 실패·재시작, 새 로컬 저장, 계정 전환과 전체 재검증을 검증한다.
- Firebase 에뮬레이터는 실제 보안 규칙 아래에서 동일 timestamp의 문서 페이지 조회, 고정 상한, 재조회와 다른 계정 접근 거부를 검증한다.

계수는 테스트 데이터에 대한 반환 문서 수와 SQLite 작업 수 기준이다. 실제 기기의 처리 시간이나 Firebase 청구 금액을 측정한 결과와는 구분한다.

변경 전 구조와 회귀 테스트의 비교:

| 조건 | 변경 전 | 변경 후 검증 |
|---|---|---|
| 1,000건 복원 후 변경 없는 자동 조회 | 기록 1,000건 전체 조회 | 최신 위치 확인 1건 + 마지막 시각 묶음 1건, 전체 조회 추가 없음 |
| 동일 내용 재반영 | owner 전체 삭제 및 기록 재삽입 | 기록 쓰기·삭제·화면 알림 없음 |
| 기록 1건 변경 | 전체 owner 기록 교체 | 해당 ID만 조회·반영, 다른 기록·사진 보존 |
| 로드된 Outbox의 상태 1건 변경 | 전체 대기열 조회·디코딩 | 단건 SELECT 1회 + UPDATE 1회, payload 재쓰기 없음 |

완료 이력이 긴 대기열도 미완료 항목의 삽입 순서 인덱스를 사용한다. 다음 전송 항목이나 같은 기록의 후속 요청을 찾기 위해 완료 이력 전체를 매번 복사·순회하지 않는다.

## 실제 기기 확인

같은 유료 계정으로 A/B 기기를 로그인하고 앱을 다시 실행한다.

1. 첫 동기화 후 기존 기록과 A에 저장된 사진이 정상적으로 보이는지 확인한다. 변경 없이 자동 동기화를 여러 번 실행해도 기록이 중복되거나 사라지면 안 된다.
2. B에서 기록 하나를 생성·수정·삭제하고 A로 돌아온다. 각 변경이 반영되고 다른 기록·기기 사진은 유지되어야 한다.
3. A를 오프라인으로 두고 기록을 수정한 뒤 연결을 복구한다. 대기열 전송과 기존 충돌 해결 흐름이 정상이어야 한다.
4. 여러 기록을 동기화하는 도중 연결을 끊거나 앱을 종료한다. 다시 실행하고 연결하면 기록이 빠지거나 중복되지 않고 동기화가 완료되어야 한다.
5. A/B에서 같은 기록을 수정하여 충돌을 만들고 내 변경·상대 변경·병합을 확인한다. 기존 선택 결과와 사진 보존 동작이 유지되어야 한다.
6. 동기화 화면에서 수동 동기화를 실행한다. 전체 재검증 후에도 기록·삭제 상태·사진이 일치해야 한다.
7. 다른 계정으로 로그인한다. 이전 계정의 기록이나 동기화 진행 상태가 섞이면 안 된다.

기존 서버 쓰기 규칙과 문서 형식은 유지하며, 이 변경을 위한 운영 Firebase 배포는 필요하지 않다. 다음 단계의 31일 캐시·과거 월 조회 정책은 이 문서의 체크포인트와 캐시 초기화 의미를 기준으로 별도 구현한다.
