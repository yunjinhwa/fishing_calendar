# 위치 좌표 저장

출조 기록에 선택적 WGS84 위도·경도를 추가한다. 기존 장소 이름은 계속 필수이며, 좌표를 모르는 경우에는 장소 이름만 입력해 저장할 수 있다. 지도·장소 검색·GPS에서 좌표를 선택하는 방법은 [카카오 지도 연결](kakao_map_setup.md)을 참고한다. 이 문서는 좌표 저장·검증·동기화의 기반을 설명한다.

## 입력과 기록 모델

- `FishingRecord.latitude`, `longitude`는 선택적 `double`이다.
- 두 값이 모두 없거나, 두 값이 모두 있는 경우를 허용한다. 한쪽만 입력하면 저장하지 않는다.
- 위도는 -90~90, 경도는 -180~180을 포함하며 0과 음수도 허용한다. 문자열·범위 초과·NaN·무한대는 저장하지 않는다.
- JSON에서 두 좌표가 없으면 기존 장소명 기록으로 읽는다. 좌표 없는 기록을 다시 저장할 때 불필요한 null 키를 넣지 않아 기존 Outbox payload를 유지한다.
- 기록 작성·수정에는 좌표 숫자 입력 UI를 표시하지 않는다. 지도에서 전달받거나 작성 화면의 장소 검색에서 선택하거나 기존 기록에서 읽은 값을 내부에 보관한다.
- 메모 등 다른 항목만 수정하면 기존 좌표가 유지된다. 장소명을 다른 곳으로 바꾸면 이전 좌표를 새 장소에 사용하지 않으며, 원래 이름으로 되돌리면 좌표 연결도 복원한다.
- 지도는 `RecordFormPage.initialLocation`, `initialLatitude`, `initialLongitude`로 선택한 위치를 전달한다.
- 상세 화면은 장소명과 별칭 아래의 카카오 지도 핀으로 저장된 위치를 표시한다. 좌표가 없는 기록은 장소명을 표시하고, 지도를 사용할 수 없는 경우에는 안내를 표시한다. 저장한 좌표의 정밀도는 유지한다.

## 기록 작성에서 위치 검색

기록 작성·수정 화면의 위치 입력칸 옆 검색 버튼으로 장소 또는 주소를 찾는다. 기록 탭·도감·지도·캘린더 등 어떤 경로로 들어왔는지와 관계없이 같은 기능을 사용한다. 기존 [카카오 지도 설정](kakao_map_setup.md)과 검색 게이트웨이를 재사용하며 새 인증키나 의존성, DB 변경은 필요하지 않다.

- 검색 결과나 지도에서 위치를 선택하고 **이 위치 사용**을 눌러야 장소명과 좌표가 함께 반영된다. 같은 장소 이름이라도 좌표가 달라지면 새 좌표를 사용한다.
- 검색 결과 중 한 곳을 눌러도 다른 결과는 유지되어 재검색 없이 선택을 바꿀 수 있다. 선택 항목은 목록 안의 강조 테두리로 표시하며, 상단에 같은 장소를 중복 표시하지 않는다. 검색어 변경·새 검색·지도 직접 선택 시에는 이전 결과를 정리한다.
- 검색 취소·뒤로가기·직접 입력으로 돌아가기는 작성한 내용과 사진을 유지한다. 검색 결과를 선택한 것만으로 기록이 저장되지는 않는다.
- 위치를 확정하면 출조 시작 시각에 맞는 날씨와 기온을 조회한다. 기존 현재 예보와 과거 관측 서비스를 사용하며, 바다로 확인된 위치에는 가까운 관측소 기준 물때와 해당 시각의 수온도 채운다.
- 확정한 장소나 시작 시각이 바뀌면 이전 자동 입력값을 지우고 새 조건의 정보를 조회한다. 장소를 직접 입력하면 검색 좌표 연결과 자동 입력값을 해제한다. 직접 입력한 값과 수정 중인 기록의 저장된 값은 유지한다. 조회할 수 없는 값은 직접 입력할 수 있다.
- 검색을 사용할 수 없어도 기존 위치 직접 입력은 가능하다. 검색 중 계정이나 편집 원본이 바뀌면 이전 검색 결과를 적용하지 않는다.
- 지도 탭과 검색 화면은 같은 지도 유지 호스트를 사용한다. 검색 중 로딩·오류 표시가 추가되거나 결과 목록을 길게 스크롤해도 지도와 진행 중 검색 연결을 유지한다.

기기에서는 다음 흐름을 확인한다.

1. 기록 탭·도감·지도에서 각각 작성 화면을 열고 위치를 검색·선택한다. 검색 시작이나 결과 목록 스크롤로 지도가 다시 로딩되지 않아야 하며, 저장 후 상세와 재실행에서 선택한 장소·좌표가 유지되어야 한다.
2. 어종·메모·사진을 넣은 뒤 검색을 취소한다. 기존 내용이 유지되고 직접 입력으로도 저장되어야 한다.
3. 바다와 민물 위치를 각각 확정한다. 출조 시작 시각에 맞는 날씨·기온이 들어가고, 물때·수온은 바다에서만 제공되는지 확인한다. 장소나 시작 시각을 바꿨을 때 이전 자동 값이 다시 나타나지 않고 직접 입력한 값은 유지되어야 한다.
4. 기존 기록에서 위치만 검색해 변경하고 저장한다. 나머지 기록 내용은 유지되며, 유료 계정에서는 위치와 좌표가 함께 동기화되어야 한다.

## 위치 별칭

기록 작성·수정 화면에서 **위치 별칭 (선택)**에 나만의 장소 이름을 입력할 수 있다. 별칭은 기록마다 저장되며, 비우면 삭제된다. 기록 목록과 상세에서 별칭을 확인하고, 기록 검색에서는 실제 장소명과 별칭을 모두 검색할 수 있다. 지도 좌표와 외부 데이터는 실제 장소를 기준으로 적용한다.

SQLite v7은 기존 기록을 유지하며 선택적 별칭 컬럼을 추가한다. 유료 기록의 별칭을 동기화하려면 새 Firestore 규칙을 배포하고 동기화에 사용하는 기기의 앱을 모두 갱신해야 한다. 별칭이 있는 기록에는 v3의 선택 필드 `locationAlias`가 추가되며 이전 앱은 이 필드가 있는 기록을 읽을 수 없다.

## SQLite와 서버 형식

SQLite v6에서 `fishing_records.latitude`, `longitude`를 nullable REAL로 추가한다. 기존 본문을 다시 만들지 않고 컬럼을 추가하며, 기존 기록의 두 좌표는 null이다. 기존 조과·사진·독립 사진 아카이브·Outbox·무료 변경 이력·충돌·버전 및 증분 체크포인트는 유지한다. 새 DB와 업그레이드 DB에 같은 좌표 쌍·범위 제약을 적용한다.

Firestore 경로와 소유권은 기존과 같다.

```text
users/{firebaseUid}/records/{recordId}
```

| 기록 종류 | schemaVersion | 좌표 필드 |
|---|---|---|
| 장소명만 있는 활성 기록 | 1 | 없음, 기존 20개 필드 |
| 좌표가 있는 활성 기록 | 2 | latitude·longitude 숫자 쌍, 총 22개 필드 |
| 삭제 tombstone | 1 | 없음, 기존 삭제 형식 |

좌표를 추가하거나 지우면 서버의 기록 `versionNo`도 기존 수정 정책대로 증가한다. 두 좌표를 제거한 활성 기록은 v1 형식으로 저장한다. 서버 v1 기록을 임의로 일괄 변환하거나 기존 장소명에서 좌표를 추측하지 않는다. 잘못된 스키마·추가 필드·한쪽 좌표·범위 초과는 서버 규칙과 앱 읽기 검증에서 거부한다.

좌표가 있는 변경 지문에는 두 좌표도 포함한다. 같은 Outbox ID에 다른 좌표를 넣어 처리 영수증을 재사용할 수 없다. 기존 무좌표 요청의 지문 형식과 해시는 유지하므로 이전 앱에서 저장된 요청도 기존 재시도 절차를 따른다.

## 동기화·충돌·캐시

좌표는 유료 Outbox와 무료 기간 변경 이력의 payload에 포함한다. 앱 재실행·재승급·서버 값 적용·본문 캐시 재복원에서도 유지한다. 기기 사진을 합쳐 기록을 재구성하는 경로에서도 서버의 위치 좌표를 보존한다.

충돌 해결의 `위치` 항목은 장소명·위도·경도를 한 묶음으로 선택한다. 같은 장소 이름이라도 좌표가 다르면 차이를 표시한다. 상대의 무좌표 위치를 선택하면 내 좌표도 제거하고, 내 위치를 선택하면 내 좌표를 함께 유지한다. 위도와 경도를 다른 출처에서 따로 선택해 섞지 않는다.

## 배포와 기기 호환

이번 앱은 기존 v1 기록과 새 v2 기록을 모두 읽는다. **기존 앱 바이너리는 v2 기록을 읽지 못하므로 좌표가 있는 기록을 사용하기 전에 모든 테스트 기기를 새 빌드로 갱신해야 한다.** 운영 전환에서도 기존 클라이언트 업데이트를 먼저 확인해야 한다.

프로젝트 폴더에서 다음 명령으로 수정된 Firestore 보안 규칙을 먼저 배포한다. 이 브랜치를 위한 추가 복합 인덱스는 없다.

```powershell
& "$env:APPDATA\npm\firebase.cmd" deploy --only 'firestore:rules' --project fishingbuild
```

SQLite는 앱 실행 시 자동 업그레이드한다. 별도 SQL 설치나 수동 데이터 삭제는 필요 없다. 이번 작업에서 운영 규칙 배포와 서버 데이터 변경은 실행하지 않았다.

## 실제 기기 테스트

현재 화면 정리에 맞춘 상세 절차는 [지도·기록 화면 정리](map_record_ui.md)를 참고한다. 아래 서버 형식·규칙 배포 설명과 최초 검증 기록은 좌표 기능 도입 당시 기준이다. 현재 서버 저장 계약은 [Firestore 기록 스키마](firestore_record_schema.md)를 따른다.

1. **기존 기록:** 새 앱으로 실행하고 이전 기록·사진·과거 월을 조회한다. 장소 이름만 있는 기록이 유지되고 메모를 수정해도 저장되어야 한다.
2. **좌표 저장:** 지도에서 장소를 선택하고 기록 작성으로 이동한다. 저장·재실행 후 상세 화면의 지도 핀이 같은 위치에 있는지 확인한다. 무료 계정에서도 기기에 저장할 수 있어야 한다.
3. **검증:** 좌표 없이 장소 이름만 입력한 기록을 저장한다. 잘못된 전달 좌표의 쌍·범위·유한성 거부는 자동 테스트로 확인한다.
4. **보존·제거:** 좌표 있는 기록의 메모만 수정해 저장하면 좌표가 유지되어야 한다. 다른 장소명으로 바꿔 저장하면 원래 좌표가 제거되어야 한다.
5. **기기 간 동기화:** 같은 유료 계정의 두 기기에서 지도 위치를 포함한 기록이 동일하게 반영되는지 확인한다. 현재 schemaVersion은 위의 최초 형식 표 대신 최신 저장 계약을 참고한다.
6. **오프라인·무료 이전:** 좌표가 있는 기록을 오프라인에서 수정한 뒤 재실행·연결 복구한다. 대기열과 좌표가 유지되어 전송되어야 한다. 무료에서 좌표 기록을 만들고 유료로 바꿔도 두 값이 함께 이전되어야 한다.
7. **충돌:** 두 기기에서 같은 기록의 위치를 서로 다르게 수정한다. 내 변경·상대 변경·직접 병합의 위치 선택에 따라 장소명과 좌표가 함께 반영되어야 한다.

## 자동 검증

2026-11-21 기록 작성 위치 검색 검증: 신규 28개와 기존 관련 회귀 테스트 213개, 합계 **241개 통과**. `flutter analyze --no-pub` 문제 없음. 검색 결과 확정·취소·실패·늦은 응답, 같은 이름의 다른 좌표, 무료/유료 저장과 Outbox, 자동 입력 해제·수동 값 보존, 사진·초안 보존, 계정 변경·편집 충돌을 검사했다. 전체 앱 테스트 일괄 실행과 실제 기기의 카카오 지도 검색은 이번 검증 범위에 포함하지 않았다.

같은 날 추가 검증: 상태가 있는 지도 대역으로 검색 시작 시 지도가 두 번 생성되는 실패를 먼저 재현했다. 고정 키와 기존 지도 탭의 유지 호스트를 공유하도록 수정한 후, 로딩 중 연결 유지·결과 스크롤·화면 종료 시 해제의 신규 2개 검증을 포함해 검색·폼·기존 지도 테스트 **44개 통과**. 정적 분석 문제 없음. 실제 기기에서는 앱을 다시 실행해 같은 검색어로 확인한다.

2026-11-01 검증: 신규 테스트 40개를 포함해 전체 **434개 통과**, `flutter analyze --no-pub` 문제 없음. 로컬 데모 프로젝트의 Firebase Auth·Firestore 보안 규칙 스모크 테스트 통과. 실제 기기 확인과 운영 규칙 배포는 별도 진행한다.

flutter test --no-pub --concurrency=1
