# 첫 동기화 충돌 해결 후 재시도 복구

브랜치: `fix/initial-sync-conflict-retry` · 대상: [최초 감사](pre-release-audit.md)의 A-02.

## 수정한 문제

첫 실제 서버 동기화가 완료되기 전에 무료→유료 이전 요청이 충돌하고 사용자가 **서버 기록 사용**을 선택하면, 다음 동기화가 이미 해결한 요청을 다시 전송했다. 서버에 커밋한 요청이 아니므로 처리 영수증이 없고 기준 버전도 오래되어 다시 충돌했으며, 기존 충돌 이력의 UNIQUE 제약에 걸려 Outbox가 `sending` 상태로 남을 수 있었다.

## 처리 방식

- SQLite의 해결 이력에서 **같은 소유 계정·기록·요청 ID**에 대한 `resolved` / `useTheirs`를 확인한다. 해당 이전 요청은 서버 기록 채택으로 종결된 것으로 처리하여 첫 동기화의 재전송 대상에서 제외한다.
- 이전 버전에서 같은 문제로 `sending`·`failed` 상태가 된 요청도 위 증거가 있을 때만 복구한다. 요청의 상태·오류만 정리하고 ID·기준 버전·본문·재시도 횟수는 유지한다. 이후 사용자가 만든 수정·삭제 요청을 함께 성공 처리하지 않는다.
- 서버에 실제 반영했거나 과거 개발용 모의 처리로 성공한 일반 요청은 기존 재전송·영수증 검증을 유지한다. 초기 동기화 완료 표식을 앞당기지 않는다.
- 원래 삭제 요청이 충돌한 뒤 살아 있는 서버 기록을 채택한 경우에도, 채택한 본문과 최신 요청의 일치를 확인하여 요금제 이전을 완료한다. 같은 내용을 새 업로드로 만들지 않는다.
- 첫 동기화 준비는 SQLite 트랜잭션 안에서 최신 요청·기록을 읽는다. 이전 완료 처리에서 복구한 Outbox는 커밋 후 메모리에도 반영한다.
- 서버 기록 조회·채택 중 세션이나 동기화 게이트웨이가 바뀌면 처리를 중단한다. 같은 계정으로 나갔다가 다시 들어온 경우도 이전 세션의 결과를 적용하지 않는다.

별도 SQL 설치, DB 스키마 변경, Firestore 규칙·인덱스 배포는 필요하지 않다. 사진은 기존과 같이 같은 기기에 보관한다.

## 실제 기기 확인

테스트용 유료 계정으로 두 기기에서 확인한다. 이미 첫 동기화를 마친 계정에서는 최초 이전 상태를 그대로 재현하기 어려우므로, 위 자동 테스트가 정확한 최초 동기화·기존 멈춤 상태를 검증한다. 아래는 일반 사용 경로의 회귀 확인이다. 재현을 위해 앱 데이터나 실제 서버 기록을 초기화할 필요는 없다.

1. **서버 기록 사용 후 재동기화:** 두 기기에 같은 기록을 내려받는다. A를 오프라인으로 두고 기록을 수정한 뒤, B에서도 같은 기록을 다르게 수정하고 동기화한다. A를 온라인으로 전환해 충돌을 확인하고 ‘서버 기록 사용’을 선택한다. 다시 동기화하거나 앱을 재실행해도 같은 충돌이 반복되거나 업로드 중으로 멈추지 않아야 한다.
2. **후속 저장:** 해결 후 A에서 기록을 새로 작성하거나 수정한다. 동기화가 완료되고 B에 반영되는지 확인한다. 기존 기록을 서버본으로 바꿨다면 A에 있던 사진이 유지되는지도 확인한다. 사진은 B로 전송되지 않는다.
3. **서버 삭제 채택:** A가 오프라인인 동안 기록을 수정하고 B에서는 같은 기록을 삭제·동기화한다. A를 온라인으로 전환해 충돌에서 ‘서버 기록 사용’을 선택한다. 기록이 제거되고, 재동기화·재실행 후에도 다시 나타나지 않아야 한다.

이전 버전에서 이미 멈춘 테스트 계정이 있다면 업데이트 후 동기화를 다시 실행하여 대기열이 진행되는지 추가로 확인한다. 관련 충돌 해결 이력이 없는 요청은 이번 복구 대상에 포함되지 않는다.
