## 판단

회원 상태·Firebase 인증·SQLite 기록·Outbox·Firestore 동기화·충돌 화면·탈퇴 정리까지 핵심 기반은 연결되어 있다. 다만 **원래 명세의 MVP 전체가 완료된 상태는 아니다.** 실제 지도/외부 API와 31일 캐시가 남아 있고, 일반적인 CRUD 테스트로 잡히지 않는 재승급·계정 전환·편집 중 동기화의 데이터 보존 문제를 먼저 해결해야 한다.

이번 점검은 코드와 문서 분석 및 로컬 검증이다. 성능 관련 내용은 실행 경로와 복잡도에 근거한 개선 후보이며, 실제 기기의 프레임 시간·메모리·Firestore 과금량을 측정한 결과는 아니다. 앱 코드와 서버 데이터는 이 점검에서 수정하지 않았다.

이번 감사 브랜치의 산출물은 이 보고서다. 8개 점검 항목과 UC-01~UC-34 대조, 기존 검사 및 추가 결함 재현을 완료했다. 발견한 결함의 수정과 회귀 테스트 추가는 후속 수정 브랜치에서 진행한다.

UI/입력 규칙서에 있는 비밀번호 재설정 메일 화면·소셜 로그인도 현재 구현되어 있지 않다. 조과 모델은 어종/크기(cm)/무게(g)를 저장하며 원 DB의 `quantity`, `weight_kg`와 계약이 다르다. 마릿수 필드를 추가하고 단위 변환을 명시해야 한다. API 문서의 기기·동기화 세션/이력·알림 읽음 처리 등도 현재 단순화된 구조와 대응 정리가 필요하다.

## 2. 먼저 해결할 결함과 데이터 보존 위험

우선순위: P1=계정 간 혼입·데이터 유실·동기화 고착, P2=오류 처리·누적 비용·명세 누락, P3=정리 작업. 정적 경로 분석과 실행 재현은 구분한다.

### F-01 · P1 · 마이그레이션 중 계정이 바뀌면 소유권이 섞일 수 있음

- 근거: `lib/data/services/plan_policy_service.dart:136`의 루프는 시작 시 A 계정의 기록 목록을 잡는다. `:170`에서 매 반복 현재 owner, `:190`/`:206`에서 현재 memberId를 다시 읽고, DB await 이후에도 세션 동일성을 검사하지 않는다. `OutboxRepository.replaceItem`도 현재 owner를 사용한다(`lib/data/repositories/outbox_repository.dart:74`).
- 조건: 여러 기록의 마이그레이션 도중 로그아웃/다른 계정 로그인. 다음 반복의 A 기록이 B 소유 Outbox로 작성되거나 owner와 userId가 달라질 여지가 있다. Firestore UID 규칙은 이미 B 소유로 잘못 만들어진 payload의 출처를 판별할 수 없다.
- 권고: 작업 시작 시 `(uid, ownerKey, sessionGeneration)` 고정, 모든 저장 API에 명시 전달, await 이후·트랜잭션 진입 시 동일 세션 확인. 마이그레이션 자체의 중복 실행도 직렬화한다.
- 검증 수준: 코드 경로 분석. 일반 sync의 계정 전환 테스트는 있지만 마이그레이션 루프 중 전환 테스트는 없다.

### F-02 · P1 · 같은 Outbox ID의 payload를 바꿔 재시도가 영구 실패할 수 있음

- 근거: `plan_policy_service.dart:203`은 기존 ID/baseVersion을 그대로 두고 payload를 교체한다. `lib/data/remote/firestore_record_sync_gateway.dart:487` 부근의 영수증 검증은 기존 지문과 다르면 `idempotency-conflict`로 거절한다.
- 조건: 서버에는 업로드가 끝났지만 응답 유실/앱 종료로 로컬이 대기 상태 → 오프라인 수정 → 마이그레이션 재개가 동일 ID의 내용을 변경 → 재시도 거절. 뒤 항목도 전송되지 않을 수 있다.
- 권고: 전송을 시도한 mutation은 불변으로 유지한다. 영수증으로 기존 성공을 복구하고 새 수정은 새 ID/후속 버전으로 큐에 추가한다.
- 검증 수준: 코드 경로 분석. `test/plan_policy_test.dart:505`는 오래된 migration payload 교체만 검증하며 서버 영수증이 이미 존재하는 경우는 빠져 있다.

### F-03 · P1 · 열린 편집 화면이 다른 기기의 수정을 충돌 없이 덮을 수 있음

### F-04 · P1/P2 · 재시작 재승급과 무료 기간 삭제의 복구 경계

- 권고: 업그레이드 전 무료 원본의 최신 상태와 삭제 이력을 먼저 확정하고 이후 reconciliation을 수행한다. 무료 기간 변경/삭제 이력을 추적하되 무료 상태에서 서버 쓰기는 하지 않는다.
- 검증 수준: **조건 A는 FakeAuthGateway와 테스트 SQLite를 사용해 실행 재현했다.** 최신 무료 수정이 이전 유료 수정으로 덮였으며, 마이그레이션 payload와 SQLite 재로드 결과에도 이전 값이 남았다. 조건 B는 코드 경로 분석이며 기대 동작에 대한 정책 확정이 필요하다.

## 3. DB·Firestore 호출과 알고리즘

N=기록 수, C=전체 조과 수, H=Outbox 전체 이력 수, Q=이번 전송 대상 수, D=화면에 보이는 날짜 수, S=어종 수. 아래 복잡도는 데이터 접근/반복 구조 기준이며 실측 시간이 아니다.

| 항목 | 현재 구조·근거 | 개선 방향 |
|---|---|---|
| F-07 전체 동기화 | `firestore_record_sync_gateway.dart:142`에서 전체 컬렉션을 서버 조회. `record_sync_service.dart:327`, `fishing_record_repository.dart:186`에서 로컬 전체 삭제 후 본문/조과/사진/메타데이터 재삽입 | 변경 시각+ID 커서 기반 페이지 조회, 변경 ID만 upsert/delete. 첫 전체 복구와 일상 증분 동기화 분리. 삭제 tombstone·커서 원자 갱신·캐시 축출의 복구 의미를 함께 설계 |
| 31일 캐시 | `user_plan_policy.dart:51`에 값만 선언되고 실제 사용 경로 없음. 오래된 기록/메타데이터 전체를 로컬과 메모리에 보관 | 31일 범위와 미전송/미해결 데이터 보호 정책, 과거 월 on-demand 조회. 단순 오래된 행 삭제만 하면 안 됨 |
| Outbox 갱신 | `outbox_repository.dart:28`, `:77`에서 한 항목 상태를 바꿀 때마다 전체 이력을 다시 읽고 JSON 복원. Q번 전송에 O(Q·H) 이상의 반복 작업 | 상태 행만 UPDATE, 메모리 해당 항목만 교체, 대기 상태 인덱스/페이지 사용. 성공 이력은 필요한 복구 증거를 남긴 뒤 정리 |
| 마이그레이션 목록 | 기록마다 전체 Outbox 필터링, 완료 확인도 record마다 `items.any`: O(N·H) | recordId별 Map과 성공 Set을 먼저 만들어 O(N+H) 조회. F-01/F-02의 정확성을 먼저 보장 |
| 캘린더 | `calendar_page.dart:233`에서 각 날짜마다 전체 기록 검색: O(D·N). 같은 달 리빌드마다 반복 | 표시 월과 겹치는 기록만 조회, 날짜별 요약 인덱스를 한 번 만들고 기록/월 변경 시만 갱신. 긴 기간 기록은 현재 표시 월로 잘라 인덱싱 |
| 검색 | `record_search_page.dart:59`에서 매 입력/리빌드에 전체 필터와 정렬: O(N+C+R log R), R=결과 수 | 날짜 경계는 루프 밖 계산, 검색 debounce, 저장소 revision+필터로 결과 캐시. 대량 데이터에는 SQL 필터·정렬·페이지 조회 |
| ID 조회 | `fishing_record_repository.dart:87`은 선형 탐색 O(N) | recordId→record Map으로 반복 단건 조회를 평균 O(1)로 변경 |
| 기록어 | `personal_best_repository.dart:16`은 어종별 Map으로 한 번 집계하고 S개 정렬: O(N+C+S log S) | 집계 방식 자체는 적절하다. 무조건 복잡한 알고리즘으로 교체할 필요 없음. 데이터/정렬 기준 변경 때만 재계산 |

`syncNow`는 진행 중 Future를 공유하여 동시 실행을 합치고 있다(`record_sync_service.dart:164`). SQLite도 owner/date 및 outbox 상태 인덱스가 있다. 이미 있는 방어를 유지하면서 실제 쿼리가 해당 인덱스와 증분 경로를 사용하도록 개선하는 것이 우선이다.

서버 영수증과 tombstone은 중복 전송·삭제 전파를 보장하는 데이터다. 비용만 보고 무조건 삭제하면 오래된 기기의 재전송이 잘못 적용될 수 있으므로 보존 기간과 클라이언트 동기화 기준을 먼저 설계해야 한다.

## 4. 화면 리빌드·메모리·불필요 코드

- `CalendarPage`, 검색 화면, 기록어 화면은 저장소 변경을 넓게 구독한다. 전체 동기화 후 불필요하게 같은 데이터로 notify할 때도 계산과 리빌드가 재실행된다. 변경된 ID/실제 값 비교와 구독 범위 축소를 F-07과 함께 적용한다.
- `AppShell`은 `IndexedStack`으로 5개 탭을 유지한다. 탭 상태 보존을 위한 선택이므로 자체가 누수는 아니다. 다만 숨겨진 탭도 구독/초기화가 유지된다. 지도 API 도입 시 방문 전 API 호출을 피하도록 지연 초기화와 데이터 서비스 캐시를 고려한다.
- 캘린더 탭의 `calendarRefreshKey` 변경은 위젯을 재생성한다(`app_shell.dart:153`). 저장소 listener와 겹치는 갱신이므로 상태 초기화가 필요한 경우에만 유지한다.
- 화면 TextEditingController, 캘린더/검색/충돌 listener, 앱 lifecycle observer, 네트워크 subscription에는 해제 코드가 있다. 이번 정적 점검으로 명백한 일반 listener 누수는 발견하지 못했다. 장시간 메모리 프로파일링을 한 것은 아니다.
- `_recordsByOwner`, `_itemsByOwner` 등 계정별 메모리 Map은 로그아웃 시 퇴거하지 않는다. 계정을 계속 바꾸면 방문한 계정의 데이터가 프로세스에 누적된다. 활성 계정만 유지하거나 제한된 LRU로 관리하되 진행 중 작업의 명시적 owner 참조를 보장한다.
- 사진 썸네일은 표시가 96×96이어도 `Image.file`에 decode 크기 제한이 없다(`record_form_page.dart:977`). 고해상도 원본 여러 장은 불필요한 메모리를 사용할 수 있다. 실제 화면 크기×기기 배율에 맞춘 `cacheWidth/cacheHeight` 또는 별도 썸네일이 적절하다. 용량 10 MiB 제한은 디코딩 픽셀 메모리 제한과 다르다.
- 앱 진입점의 import/조건부 import 도달성 조사에서 `lib/presentation/common/placeholder_screen.dart`는 미사용으로 확인됐다. `CalendarSettingsPage`는 주석 처리된 import를 제외하면 연결이 없고 UI도 고정 상태다. 삭제 또는 실제 설정 구현으로 정리한다.
- 현재 앱 소스에서 사용되지 않는 선언 의존성: `go_router`, `flutter_riverpod`, `dio`, `freezed_annotation`, `json_annotation`, `table_calendar`, `intl`, `cupertino_icons`. 생성 코드가 없는 현재 구조에서 `build_runner`, `freezed`, `json_serializable`도 사용 용도를 확인 후 정리할 수 있다. 단순 의존성 제거가 곧 런타임 성능 향상을 보장하는 것은 아니다.
- `_InfoCard`, `_InfoRow`, `_SectionTitle`, 날짜/시간 포맷 코드가 여러 페이지에서 반복된다. 동일한 표현만 공통화하고 화면별 차이까지 무리하게 일반화하지 않는다. 개인 기록어 `_shouldReplaceBest`의 `sourceRecord` 인자도 사용되지 않는다.
- 필수 환경값 검증은 화면과 `FishingRecordValidator`/Firestore 규칙이 일치하지 않는다. 화면은 필수를 요구하지만 도메인 validator와 규칙은 tide/weather/온도의 null을 허용한다. 레거시 읽기 허용과 신규 쓰기 검증을 구분해 한 계약으로 정리해야 한다.

## 5. 인증·요금제·동기화 접근 제한

확인한 방어:

- 비회원 탭/저장 진입은 접근 가드가 있고 mutation 서비스도 회원 권한을 확인한다.
- 일반 무료 회원은 remote gateway를 호출하지 않는다. 유료 여부는 서버 entitlement와 만료 시각으로 판정하며, 클라이언트의 entitlement 생성/수정은 Firestore 규칙에서 차단한다.
- Firestore 기록/영수증 접근은 요청 UID 소유권과 활성 유료 권한을 확인한다. 탈퇴 표식이 있으면 정상 기록 접근을 막고 탈퇴 정리 경로만 허용한다.
- 기록+영수증 원자 쓰기, 버전 연속성, 삭제 tombstone, 별도 계정별 SQLite owner 구분이 존재한다.
- 일반 동기화는 작업 시작 owner/uid를 캡처하고 await 이후 세션을 확인한다. 이 방식을 마이그레이션에도 일관되게 적용해야 한다(F-01).
- 개발용 로컬 인증/플랜은 테스트 용도로 남아 있다. release는 기본 Firebase 활성화이며 초기화 실패 시 로컬 인증으로 자동 강등하지 않는다.

미확인/보완: 실제 배포된 규칙 버전과 운영 Firebase 데이터는 조회하지 않았다. 오프라인 동안 다른 기기의 탈퇴/플랜 변경을 즉시 아는 것은 불가능하므로, 네트워크 복구 시 재확인과 로컬 데이터 정리 경계가 중요하다. UI에서의 접근 차단만으로 장시간 작업의 계정 소유권 보호를 대신할 수 없다.

## 6. 빠진 핵심 테스트와 검증 결과

추가할 회귀 테스트:

1. 마이그레이션 DB await 사이 A→B 계정 전환: 어느 계정에도 payload 혼입 없음.
2. 서버 커밋 성공/ACK 유실 → 로컬 수정 → 마이그레이션 재개: 이전 영수증 복구 및 새 수정 전송.
3. v1 편집 화면을 열고 v2 pull 후 저장: 조용한 덮어쓰기 차단.
4. 무료 기간 변경 후 앱 종료 상태에서 재승급: 시작 순서가 최신 로컬 변경을 보존.
5. 무료 기간 삭제 후 재승급: 합의한 삭제/서버 보존 정책대로 처리.

## 7. 감사 완료 후 권장 작업 순서

아래 수정과 회귀 테스트는 후속 작업이며 브랜치명은 제안이다. 1~4는 현재 기능의 결함 수정 순서다. 5~7은 관련 성능·정책·기능 개발의 연결 관계를 제안하며, 모든 최적화를 새 기능의 선행 조건으로 두지는 않는다. 무료 기간 삭제 후 재승급의 기대 동작(F-04 조건 B)은 수정 전에 정책을 확정해야 한다.

1. `fix/plan-migration-integrity`: F-01/F-02/F-04 및 해당 재현 테스트. 계정 고정·불변 mutation·재승급 순서/삭제 정책을 함께 다룬다.
2. `fix/record-edit-version`: F-03. 편집 기준 버전 전달과 원격 변경 안내.
3. `fix/record-save-recovery`: F-05 및 작성 취소 확인. DB 오류/중복 저장 회귀 테스트.
4. `fix/local-photo-cleanup`: F-06. 임시 파일과 참조 보호 기반 정리.
5. `perf/incremental-record-sync`: F-07, Outbox 부분 갱신, 조회/계산 캐시. 변경 전후 DB 작업 수와 profile 지표 비교.
6. `feature/paid-cache-policy`: 31일 캐시·과거 월 조회·축출/재복원 정책. 증분 동기화에서 축출된 기록이 필요할 때 다시 내려올 수 있어야 한다.
7. 실제 지도/외부 데이터 연동 후 도감·공유 등 후속 기능. REST/ERD/LWW 및 사진 정책 문서는 현재 선택한 구현과 일치하도록 먼저 갱신한다.

미사용 의존성/공통 UI 정리는 위 데이터 보존 수정과 분리하면 리뷰 범위를 작게 유지할 수 있다.
