# Firestore 조과 형식 검증

브랜치: `fix/firestore-record-schema` · 대상: [최초 감사](pre-release-audit.md)의 A-03.

## 수정한 문제

기존 규칙은 `catches`가 최대 100개인 배열인지 확인했지만, 각 항목의 객체 형태와 어종명·크기·무게 타입은 검사하지 않았다. 따라서 `catches: [42]` 같은 문서가 저장될 수 있었으며, 앱에서 읽을 때 해당 조회 전체가 실패했다.

읽기 실패 시 기존 로컬 기록을 보존하는 경계는 유지한다. 손상된 문서를 조용히 생략한 결과로 로컬 기록을 삭제하거나, 실패한 페이지 너머로 체크포인트를 옮기지 않는다.

## 저장 계약

| 구분 | 이전 기록 v1/v2 | 새 기록 v3 |
| --- | --- | --- |
| 조과 필드 | `catches`: 객체 배열 | `catchesJson`: 검증 가능한 JSON 문자열 |
| 좌표 | v1 없음 / v2 위도·경도 | 위도·경도를 함께 저장하거나 함께 생략 |
| 새 앱에서 읽기 | 유지 | 지원 |
| 새 규칙 적용 후 활성 기록 쓰기 | 거부 | 허용 |

삭제 tombstone은 v1을 유지한다. SQLite 스키마, 로컬 모델, 기존 Outbox 본문, 영수증의 변경 지문은 변경하지 않는다. 기존 기록은 읽을 때 강제 변환하지 않으며, 새 앱에서 수정하여 서버에 반영할 때 v3으로 저장한다. 추가 문서·조회·백엔드·Firebase Storage를 도입하지 않는다.

### 배열을 그대로 검증하지 않은 이유

Firestore Rules는 반복문과 배열 전체 항목의 타입 검사를 제공하지 않으며 요청당 평가 식 수에 제한이 있다. 에뮬레이터에서 기존 배열을 100회 검사하도록 직접 연결하면 컴파일 실패가 발생했고, 함수 그룹으로 나눈 엄격·최적화 변형도 정상 조과 100개에서 1,000식 한도를 초과했다. 조과 한도를 줄이는 대신 단일 문자열의 전체 문법을 검증한다. 참고: [규칙 한도](https://firebase.google.com/docs/firestore/quotas), [규칙 언어](https://firebase.google.com/docs/rules/rules-language), [필드 검증](https://firebase.google.com/docs/firestore/security/rules-fields).

### JSON 검증 방식

- 최대 조과 100개, 어종명은 공백만으로 구성할 수 없으며 UTF-16 기준 100자까지 허용한다.
- 어종명은 JSON의 `\uXXXX` 이스케이프로 기록한다. 한글·따옴표·역슬래시·이모지를 보존하면서 필드 경계와 글자 수를 검증할 수 있다.
- 선택적 크기는 `null` 또는 0 이상의 유한한 double이다. 쓰기는 17자리 유효 숫자의 지수 표기를 사용하며, 최소 양수·최대 유한 값·음의 0을 보존한다.
- 선택적 무게는 `null` 또는 0 이상 signed 64-bit 정수 범위다. 소수·문자열·음수·범위 초과를 거부한다.
- 필드 누락·추가, 숫자/문자열 조과 항목, 101개 이상, 손상된 JSON을 거부한다. 크기 숫자의 안전한 반올림 표현은 읽을 수 있으며, 재인코딩 문자열의 완전한 동일성을 읽기 조건으로 삼지 않는다.
- 정규식 길이와 RE2의 중첩 반복 제한을 피하기 위해 문법·개수·이름 길이를 나누어 검사한다.

앱 코덱에서 규칙의 검증 문법을 생성한다. 문법을 바꿀 때 수작업으로 양쪽을 고치지 않는다.

```powershell
dart run tool/generate_catches_rules.dart
dart run tool/generate_catches_rules.dart --check
```

## 오류 식별과 데이터 보존

전체·증분·월별·개별 기록 조회와 기록 변경 구독에서 잘못된 문서의 실제 ID를 오류에 포함한다. 기존 배열 형식은 `catches[1].weightG`처럼 문제 항목도 표시하며, 새 문자열 형식은 `catchesJson`을 표시한다. UID와 잘못된 본문 값은 안내에 넣지 않는다.

캘린더의 과거 월 및 검색·기록어의 전체 이력 안내에도 해당 오류를 전달한다. 재시도 성공·조회 해제·계정 전환 시 오래된 오류를 제거한다.

- 전체 조회 실패: 기존 SQLite 기록·사진·최초 동기화 표식·체크포인트 유지.
- 증분 후속 페이지 실패: 이전 정상 페이지의 체크포인트까지만 유지. 실패한 페이지의 정상 문서도 부분 적용하지 않는다.
- 월 조회 실패: 이미 받은 정상 페이지는 유지하되, 누락 기록 정리는 마지막 페이지까지 성공한 후에만 실행.
- 전체 이력 실패: 부분 스냅샷을 적용하거나 누락 기록 정리를 실행하지 않음.

이전 규칙으로 이미 손상된 문서가 저장되어 있다면 새 규칙 배포만으로 자동 복구되지는 않는다. 표시된 문서 ID로 운영자가 원본을 백업하고 실제 기록에 근거해 잘못된 필드를 복구해야 한다. 복구 시 버전과 서버 갱신 시각도 갱신하여 기기에 변경이 전달되도록 한다. 오류를 없애기 위해 조과를 임의로 삭제하거나 0으로 바꾸는 자동 처리는 하지 않는다.

## 적용 순서

**이 브랜치에서는 운영 배포를 실행하지 않았다. 새 앱의 실제 서버 테스트 전에 규칙을 배포해야 한다.** 기존 규칙은 v3 쓰기를 허용하지 않으며, 새 규칙은 느슨한 v1/v2 활성 기록 쓰기를 막는다. 테스트 기기들을 모두 새 앱으로 맞추고 전환한다. 이전 앱은 v3 기록을 읽을 수 없다.

```powershell
& "$env:APPDATA\npm\firebase.cmd" deploy --only firestore:rules --project fishingbuild
```

새 인덱스나 SQLite 마이그레이션은 필요하지 않다. 규칙과 앱을 함께 되돌릴 경우 구버전 앱이 이미 저장된 v3 문서를 읽지 못하므로, 규칙만 되돌리는 것으로 호환 문제가 해결되지는 않는다.

## 검증과 기기 확인

자동 검증은 새 코덱의 Unicode·숫자 경계, v1/v2 읽기, v3 왕복 변환과 지문 보존, 손상된 전체·후속 페이지의 SQLite 보존 및 재시도를 포함한다. `tool/firestore_rules_smoke.mjs`는 비관리자 사용자 토큰으로 정상 100개 저장과 잘못된 요청의 거부, 원자적 기록·영수증 쓰기, 계정 격리를 확인한다. 운영 데이터를 사용하지 않는 로컬 demo 에뮬레이터에서 실행한다.

2026-11-15 검증에서 전체 Flutter 테스트는 **1,409개 중 1,406개 통과·3개 실패**였다. 실패는 이전 감사부터 남아 있던 앱 정보·출처 테스트 3개와 동일하며 이번 브랜치의 수정 범위에 포함하지 않았다. 새 규칙의 로컬 Auth/Firestore 에뮬레이터 검사는 통과했다.

```powershell
flutter test --no-pub test/firestore_catches_codec_test.dart test/firestore_record_schema_test.dart test/record_schema_read_safety_test.dart test/firestore_record_codec_test.dart test/location_coordinates_firestore_test.dart test/optional_record_conditions_sync_test.dart
dart run tool/generate_catches_rules.dart --check
firebase emulators:exec --only auth,firestore --project demo-fishing-schema "node tool/firestore_rules_smoke.mjs"
```

규칙 배포와 두 기기 앱 갱신 후 테스트 계정으로 다음을 확인한다.

1. **기존 기록:** 예전 기록의 조과·선택 좌표·같은 기기의 사진이 그대로 보이는지 확인한다.
2. **작성·수정·삭제:** 조과 없이 저장하고, 크기·무게가 있거나 없는 여러 조과를 추가·수정한다. 다른 기기에도 반영되는지 확인하고 삭제도 시험한다. Firestore 활성 문서는 `schemaVersion: 3`과 문자열 `catchesJson`을 사용한다.
3. **오프라인 재시도:** 네트워크를 끄고 수정한 뒤 다시 연결한다. 중복 기록 없이 반영되고 다른 기기의 내용도 일치해야 한다.
4. **과거 조회:** 과거 월·검색·기록어에서 기존 기록을 읽을 수 있는지 확인한다. 손상 데이터 차단·복구 시험은 자동 테스트에서 수행했으므로 실제 계정에 손상 문서를 만들 필요는 없다.

최종 앱 빌드·배포 및 실제 기기 검증은 별도 단계다.
