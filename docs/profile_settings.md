# 프로필 설정과 닉네임 변경

브랜치: `feature/profile-settings` · 대상: [추가 요구사항](pre-release-additional-requirements.md)의 U-10.

내 정보의 `프로필 설정`에서 이메일을 확인하고 닉네임을 변경한다. 기존 회원 탈퇴 진입점도 프로필 설정 하단으로 옮겼다. 닉네임 변경은 무료·유료 회원 모두 사용할 수 있고 비회원·탈퇴 처리 중인 계정은 변경할 수 없다. 이메일·비밀번호 변경이나 프로필 사진 업로드는 추가하지 않는다.

## 화면 동작

- 이메일은 읽기 전용으로 표시한다. 닉네임을 수정한 뒤 `저장`을 누른다.
- 원래 닉네임과 같거나 앞뒤 공백만 달라졌으면 저장하지 않는다.
- 잘못된 입력·중복·네트워크 오류는 입력란 아래에 표시한다. 실패 시 작성 중인 입력을 유지해 다시 시도할 수 있다.
- 저장 성공 후 내 정보와 프로필 화면에 새 닉네임을 반영하고 상단 완료 알림을 표시한다.
- 저장·최신 정보 조회 중에는 입력·중복 요청·뒤로 이동을 막는다. 기존 인증 작업과 닉네임 변경도 동시에 실행하지 않는다.
- 다른 기기의 변경을 받았을 때 입력을 수정하지 않았다면 새 닉네임을 반영한다. 수정 중이면 초안을 보존하고 변경 안내를 표시한다. `최신 닉네임 불러오기`로 서버 값을 적용한 뒤 다시 수정한다.
- 화면을 연 계정·세션이 바뀌거나 탈퇴 잠금이 적용되면 기존 이메일·닉네임 입력을 숨기고 저장을 차단한다.

작은 화면·큰 글자·키보드가 표시된 상태에서도 폼을 스크롤해 사용할 수 있다.

## 회원 탈퇴 진입과 복구

- 일반 회원의 경로는 `내 정보 → 프로필 설정 → 하단 회원 탈퇴`다. 내 정보 하단에 회원 탈퇴 버튼을 직접 표시하지 않으며 로그아웃은 기존 내 정보 화면에서 제공한다.
- 탈퇴 확인창에서 현재 비밀번호와 `탈퇴` 확인 문구를 입력한다. 구버전 계정이 비밀번호 설정을 먼저 해야 하는 경우에도 기존 설정 절차를 사용한다. 확인을 취소하면 프로필 설정으로 돌아온다.
- 저장·조회·탈퇴 확인 처리가 겹치지 않도록 잠그며, 실제 탈퇴를 시작한 뒤에는 기존 확인창의 중복 제출·뒤로 이동 차단을 유지한다. 완료하면 로그인 선택 화면으로 이동한다.
- 이 기기에서 시작한 탈퇴가 중단되면 내 정보의 프로필 설정 메뉴는 열 수 있다. 프로필에서는 닉네임 입력·저장을 숨기고 `회원 탈퇴 처리가 중단되었습니다` 경고와 `회원 탈퇴 계속하기`를 제공한다.
- 다른 기기에서 탈퇴한 계정은 기존 내 정보의 전용 안내 화면에서 로그아웃만 제공한다. 탈퇴를 다시 시작하거나 `회원 탈퇴 계속하기`를 표시하지 않는다. 프로필 설정을 이미 열고 있었다면 일반 편집·탈퇴 기능을 사용할 수 없다.

비밀번호 설정·탈퇴 확인창은 [공통 계정 다이얼로그](../lib/presentation/auth/account_management_dialogs.dart)로 분리했다. 기존 [AccountDeletionService](../lib/data/services/account_deletion_service.dart)를 그대로 호출하며 서버 삭제 순서·재인증·삭제 표식·기기 정리 정책은 바꾸지 않는다. 세부 정책은 [회원 탈퇴 문서](account_deletion.md)를 참고한다.

## 닉네임 규칙

[NicknamePolicy](../lib/data/auth/nickname_policy.dart)의 기존 가입 규칙을 사용한다.

- 앞뒤 공백을 제거한 2~20자.
- 한글 완성형·영문·숫자·일반 공백·밑줄·하이픈을 허용한다.
- 중복 판정 키는 앞뒤 공백을 제거한 영문 소문자 값이다. `Fisher`와 ` fisher `는 다른 회원이 함께 사용할 수 없다.
- 같은 회원의 대소문자 표시 변경은 허용한다. 이 경우 기존 예약 문서를 삭제하지 않고 같은 키의 표시값을 갱신한다.

## 서버 정본과 원자적 변경

Firebase 사용 시 [FirebaseAuthGateway](../lib/data/auth/firebase_auth_gateway.dart)가 다음 문서를 하나의 Firestore 트랜잭션에서 처리한다.

| 문서 | 역할 |
|---|---|
| `user_profiles/{uid}` | 해당 UID의 표시 닉네임과 예약 키 |
| `nickname_claims/{nicknameKey}` | 닉네임 예약의 소유 UID와 동일한 표시값 |
| `account_deletion_requests/{uid}` | 탈퇴 잠금 확인 |

현재 프로필·기존 예약 소유권·탈퇴 표식을 확인하고, 새 이름의 중복을 검사한 뒤 새 예약과 프로필을 함께 기록한다. 예약 키가 바뀌면 이전 예약도 같은 트랜잭션에서 삭제한다. 어느 조건이 실패해도 프로필만 바뀌거나 이전 예약만 해제되지 않는다. 성공 후 이전 이름은 다른 회원이 사용할 수 있다.

편집을 시작한 닉네임과 현재 서버 닉네임이 다르면 이전 화면의 저장을 거절한다. 다른 기기가 먼저 저장한 닉네임을 늦은 요청으로 덮어쓰지 않는다.

[Firestore 규칙](../firestore.rules)은 소유 UID·탈퇴 잠금·입력 형식·프로필/예약의 정확한 표시값 일치를 검증한다. 이전 예약을 남긴 변경, 예약만 만든 쓰기, 프로필만 바꾼 쓰기와 다른 UID의 예약 탈취를 거부한다. 기존 가입 실패의 원자적 정리와 회원 탈퇴의 프로필·예약 삭제는 유지한다.

**닉네임 정본은 Firestore 프로필이다.** 변경 성공 시 Firebase Authentication의 `displayName`을 별도 서비스 호출로 즉시 수정하지 않는다. 다음 정상 로그인에서 서버 프로필을 기준으로 Auth의 표시 이름도 맞춘다. 이 보조 갱신이 일시적으로 실패해도 이미 성공한 닉네임 변경을 되돌리거나 로그인을 실패로 표시하지 않는다. Firebase Auth 콘솔의 표시 이름과 Firestore 값이 일시적으로 다를 수 있으며 앱은 검증된 프로필 값을 사용한다.

닉네임 변경으로 Firebase UID·이메일·기록 소유 키·요금제·기록·사진·Outbox를 변경하거나 이전하지 않는다.

## 세션 구독·오프라인·로컬 개발 모드

[AuthSessionRepository](../lib/data/repositories/auth_session_repository.dart)는 활성 Firebase UID의 프로필을 한 번 구독한다. 서버가 확정한 변경만 반영하며 Firestore 캐시·미확정 쓰기를 새 닉네임으로 채택하지 않는다. 로그아웃·계정/게이트웨이 변경·탈퇴 처리 시 구독을 해제하고, 이전 UID·세션의 늦은 응답과 더 오래된 변경 결과를 무시한다.

검증된 닉네임은 UID별 기기 캐시에 저장한다. 구독이나 최신 정보 조회가 실패하면 마지막 검증값을 유지한다. 서버 변경은 성공했지만 로컬 캐시 기록만 실패한 경우에도 서버의 성공을 취소하지 않는다. 온라인 재조회·재로그인으로 정본을 다시 받을 수 있다.

Firebase의 닉네임 변경은 서버 트랜잭션이 필요하므로 오프라인에서 완료 처리하거나 Outbox에 넣지 않는다. 오프라인 앱 재시작은 기존 UID별 검증 캐시를 사용할 수 있다.

Firebase가 꺼진 로컬 개발 모드에서는 같은 기기의 계정 닉네임 목록을 갱신하며 다른 계정의 중복을 검사한다. 이 모드의 중복 검사는 기기 안에서만 유효하며, 여러 기기의 전역 닉네임 예약을 보장하지 않는다.

## 규칙 적용과 자동 검증

**운영 배포는 실행하지 않았다.** 기존 규칙은 예약 키 변경을 허용하지 않으므로 실제 Firebase에서 닉네임 변경을 시험하기 전에 새 규칙을 적용해야 한다. 새 패키지·SQLite 마이그레이션·Firestore 인덱스 추가는 필요하지 않다.

```powershell
& "$env:APPDATA\npm\firebase.cmd" deploy --only 'firestore:rules' --project fishingbuild
```

2026-11-16 로컬 `demo-fishing-profiles` 프로젝트와 loopback Auth·Firestore 에뮬레이터에서 다음 검사를 통과했다.

| 검사 | 결과 |
|---|---|
| `tool/profile_nickname_rules_smoke.mjs` | 51개 HTTP 상태 검증 통과 |
| 기존 `tool/firestore_rules_smoke.mjs` | 기록 저장 형식·접근 제한·탈퇴 정리 회귀 검사 통과 |

닉네임 검사는 가입, 원자 변경, 이전 이름 재사용, 대소문자 변경, 중복·동시 경합, 다른 UID, 일부 문서만 쓴 요청, 표시값 불일치와 탈퇴 잠금을 다룬다. 새 검증 스크립트는 `demo-` 프로젝트와 loopback 호스트에서만 실행된다.

```powershell
& "$env:APPDATA\npm\firebase.cmd" emulators:exec --only 'auth,firestore' --project demo-fishing-profiles 'node tool/profile_nickname_rules_smoke.mjs'
```

포트 충돌을 피해야 하면 별도의 로컬 Firebase 설정을 `--config`로 지정한다. 이번 검증은 Auth 24999 / Firestore 24080 / hub 24400 / logging 24500 포트를 사용했으며 UI는 실행하지 않았다.

앱 검증 파일은 다음과 같다.

- [게이트웨이 테스트](../test/firebase_profile_nickname_gateway_test.dart): 원자 변경·중복·표시 대소문자·오래된 편집·소유권·실패·구독 필터.
- [세션 테스트](../test/profile_nickname_session_test.dart): 로컬/서버 변경·기기 캐시·인증 경합·다른 기기 반영·이전 응답 차단·구독 정리.
- [화면 테스트](../test/profile_settings_page_test.dart): 메뉴 이동·읽기 전용 이메일·입력 검증·성공/실패·중복 제출·초안 충돌·접근 제한·작은 화면과 키보드.

| 앱 검사 | 2026-11-16 결과 |
|---|---|
| 전체 Flutter 테스트 (`flutter test --no-pub`) | 1,584개 통과 |
| 정적 분석 (`dart analyze --fatal-infos`) | 문제 없음 |
| Dart 포맷·변경 공백 검사 | 통과 |

신규 테스트는 게이트웨이 10개·세션 18개·화면 10개로 총 38개다. 로컬 저장 첫 단계와 세션 저장 단계의 실패 복원, 감시 시작·종료·취소 오류, 캐시 실패 후 재시도도 검증했다. 기존 로그인·인증 경합·플랜·탈퇴·기록·사진 동작은 전체 테스트에서 함께 확인했다.

회원 탈퇴 버튼 이동 후 추가 확인(2026-11-21): 탈퇴·프로필·인증 화면 이동·사진 정리 관련 35개를 `--concurrency=1`로 순차 실행해 모두 통과했고 정적 분석도 통과했다. 탈퇴 성공 후 로그인 복귀, 중단 재개, 확인 취소와 입력 보존, 저장 중 탈퇴 차단, 계정 교체 후 이전 확인창의 삭제 차단을 포함한다. 전체 병렬 재실행은 기존 사진 I/O 검사 한 건의 시간 초과 후 진행이 멈춰 중단했으며, 해당 사진 파일 전체는 위 순차 실행에서 통과했다.

실제 기기 조작, 최종 앱 빌드와 배포는 실행하지 않았다.

## 실제 기기 확인

규칙 적용 후 테스트 계정으로 확인한다.

| 확인 항목 | 절차와 기대 결과 |
|---|---|
| 기본 변경 | 내 정보 → 프로필 설정에서 이메일이 수정되지 않는지 확인한다. 새 닉네임을 저장하면 완료 알림과 내 정보의 이름이 바뀌어야 한다. |
| 입력 규칙 | 1자·21자·허용하지 않는 기호를 입력한다. 저장을 거부하고 입력을 유지해야 한다. 원래 이름과 같거나 앞뒤 공백만 바꾸면 저장이 활성화되지 않아야 한다. |
| 중복·표시 대소문자 | 다른 계정의 닉네임을 영문 대소문자·앞뒤 공백만 바꿔 입력해도 중복으로 거부해야 한다. 자기 이름의 영문 대소문자만 변경하는 것은 허용해야 한다. |
| 이전 이름 해제 | A 계정에서 이름을 변경한 뒤 B 계정이 A의 이전 이름을 사용할 수 있는지 확인한다. A의 새 이름은 B가 사용할 수 없어야 한다. |
| 저장 중 이동 | 저장을 연속으로 누르거나 처리 중 뒤로 이동한다. 중복 변경과 화면 이탈이 발생하지 않아야 한다. 실패 후에는 입력을 유지하고 다시 시도할 수 있어야 한다. |
| 재로그인 | 변경 후 앱 재실행·로그아웃/재로그인 시 새 닉네임을 유지해야 한다. 기록·사진·요금제·동기화 대기열은 그대로여야 한다. |
| 오프라인 | 서버 값을 한 번 받은 뒤 네트워크를 끊는다. 마지막 검증 이름은 유지하며 새 변경은 실패로 안내해야 한다. 입력을 보존하고 연결 복구 후 다시 저장할 수 있어야 한다. |
| 계정·탈퇴 경계 | 프로필 화면을 연 뒤 계정이 바뀌거나 다른 기기에서 탈퇴되면 기존 계정 정보와 저장 기능을 제공하지 않아야 한다. |
| 탈퇴 위치·취소 | 내 정보 하단에는 회원 탈퇴 버튼이 없어야 한다. 프로필 설정 하단에서 회원 탈퇴를 열고 취소하면 프로필 화면과 기존 정보가 유지되어야 한다. |
| 탈퇴 확인·복구 | 잘못된 비밀번호로는 데이터가 바뀌지 않아야 한다. 탈퇴를 시작한 기기에서 처리가 중단되면 내 정보 → 프로필 설정을 열어 경고·`회원 탈퇴 계속하기`로 재개할 수 있어야 하며 닉네임은 수정할 수 없어야 한다. |
| 원격 탈퇴 안내 | 다른 기기에서 탈퇴하면 내 정보에 탈퇴 안내와 로그아웃만 보여야 한다. 프로필 설정·탈퇴 재시작·계속하기를 제공하지 않아야 한다. |
| 작은 화면 | 글자를 크게 하고 키보드를 연다. 이메일·닉네임·오류·충돌 안내와 저장 버튼을 스크롤해 확인할 수 있어야 한다. |

두 기기에서는 같은 Firebase 계정으로 로그인해 다음을 확인한다.

1. B의 프로필 입력을 수정하지 않은 상태에서 A가 닉네임을 저장한다. B의 내 정보와 프로필에도 새 이름이 반영되어야 한다.
2. B에서 초안을 입력한 뒤 A가 다른 닉네임을 저장한다. B의 초안은 유지하고 외부 변경 안내를 표시하며 바로 저장할 수 없어야 한다.
3. B에서 `최신 닉네임 불러오기`를 누른다. A가 저장한 이름으로 초기화된 뒤 다시 수정할 수 있어야 한다.
4. A·B가 거의 동시에 같은 계정의 다른 닉네임을 저장하면 먼저 확정된 변경을 이전 편집값으로 덮어쓰지 않아야 한다. 서로 다른 두 계정이 같은 이름을 요청하면 한 계정만 성공해야 한다.
